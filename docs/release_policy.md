# 提交、版本与变更日志

Try 采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)、[SemVer 2.0.0](https://semver.org/spec/v2.0.0.html) 和 [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/)。本文统一维护项目的具体约定，适用于后续提交与发布；已有提交、版本号和标签保持原记录。

## 提交

标题格式为 `type(scope)!: 描述`；`scope` 和 `!` 按需使用。描述使用中文，简要说明结果；type 与 scope 使用小写英文，scope 可使用 snake_case。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 问题修复 |
| `perf` | 性能改进 |
| `refactor` | 保持行为的代码整理 |
| `docs` | 文档与维护规则 |
| `test` | 测试 |
| `build` / `ci` | 构建、依赖或持续集成 |
| `style` / `chore` | 格式或其他维护 |
| `revert` | 撤销既有改动，正文说明对应提交与影响 |

这是项目选用的类型集合与语言约定。正文与标题空一行，按需说明原因、行为变化和验证结论；单次验证输出仍按[仓库内容规则](development.md#仓库内容)保存。

不兼容变化必须用标题中的 `!` 或页脚 `BREAKING CHANGE:` 标识。Try 还要求说明受影响的用法、数据迁移或替代方法；即使采用 `!`，也要保留这些说明。

```text
feat(packs): 支持图片题面
fix(ui): 修复卡片收起后的位置
docs: 统一提交与发布规范
```

反馈与调试先保留在工作区；需要本地检查点时保存到本地生成目录。保存里程碑或准备发布时，将同一改动的实现、必要文档和验证结论整理为一个完整提交。公开 PR 可使用 Squash and merge；整理后的标题按实际变化选择类型，正文保留同时交付的修复与不兼容变化。

一个版本可包含多个完整批次。公开或共享后的主分支保留有意义的增量历史，不为凑成“全仓库一个提交”改写既有历史。

克隆后按[开发说明](development.md#提交规范)启用现有提交钩子与[模板](commit_template.txt)。钩子检查标题格式和中文描述；改动类型、兼容性与迁移说明由审阅确认。

## 版本

程序版本使用 `MAJOR.MINOR.PATCH`，例如 `0.5.0`；Git 标签加 `v`，例如 `v0.5.0`。根 `Cargo.toml` 的 package version 是程序版本来源，发布时同步锁文件中的本项目版本。界面、内嵌版本、标签、版本化附件名称和校验记录必须对应同一版本。

兼容性以已文档化的知识包 JSON 导入导出、命令行用法、受支持平台和用户可见行为为判断依据。更新必须保留设置、题库、图片和学习记录，格式变化需要迁移与回退检查；内部 Rust 模块不构成对外库 API。知识包自身的格式版本与 Try 程序版本分别维护，格式契约见[知识包格式](knowledge_pack_format.md)。

当前 `0.x` 阶段采用以下项目约定；`1.0.0` 表示开始承诺稳定兼容性：

| 本次交付的实际影响 | 当前 `0.x` | `1.0.0` 及以后 |
| --- | --- | --- |
| 兼容的问题修复、性能或其他需要交付的兼容改进 | 增加 PATCH，如 `0.4.0 → 0.4.1` | 增加 PATCH |
| 兼容的新功能或公开功能弃用 | 增加 MINOR，如 `0.4.0 → 0.5.0` | 增加 MINOR |
| 不兼容变化，包括移除已支持的用法或平台 | 增加 MINOR，并显式标记破坏性变化和迁移方式 | 增加 MAJOR |
| 仅文档、测试或维护流程变化，未影响程序与必要分发内容 | 无需发布程序版本 | 无需发布程序版本 |

按本次发布中影响最高的变化决定版本，升 MINOR 时 PATCH 归零，升 MAJOR 时 MINOR 与 PATCH 归零。类型与影响需要一致；版本号不按提交数量、构建次数或依赖版本机械递增。独立组件维护自己的版本，Try 根据接入后的实际影响升版。

GitHub 的草稿、预发布标记与 SemVer 版本号分开处理。现有 `0.x` 沿用普通三段版本号并标记为 GitHub 预发布；若需要带独立候选编号的 SemVer 预发布，使用 `0.5.0-rc.1` 这样的后缀，验证更新排序、打包与下载匹配后再采用。`+build` 元数据不用于提示用户升级。

已公开的同一版本保持同一份程序内容与固定标签；更正程序或必要分发内容时发布新版本。说明勘误可在文档中修正，无需重新打包旧版本。

## 变更日志

[changelog.md](../changelog.md) 是人工整理的版本变化记录；GitHub Release 正文从对应版本条目提炼，保持简短，标题使用版本标签。更新说明写实际交付的变化与必要升级提示，产品介绍与使用说明留在 README 和指南中。

- 顶部保留 `[Unreleased]`，开发期间将值得用户或贡献者了解的变化放在这里。
- 依变化使用 `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、`Security` 分类，只保留有内容的分类。
- 每个公开发布的版本有独立条目，最新版本在前，标题使用 `## [版本] - YYYY-MM-DD`，日期按实际 GitHub 发布时间的 UTC 日期记录。草稿保留未发布状态，不预填已发布日期。
- 版本链接指向与上一个公开版本的比较；首版链接到对应版本页。`Unreleased` 比较最近公开版本与主分支。
- 写清结果和影响，同类变化合并表述；调试步骤、逐条 commit 日志与单次测试输出留在维护记录中。不兼容变化、弃用、移除与迁移方式必须可见。

仅维护流程或文字勘误不必占用用户更新条目。发布时将本版 `Unreleased` 内容归入带版本和日期的条目，继续保留空的 `Unreleased`，更新比较链接。首次整理旧条目时可改善格式和补充遗漏，保留已核实的版本事实。

## 发布执行

准备公开批次时先核对提交类型、是否需要升版及 `Unreleased` 内容，再按[发布检查清单](release_checklist.md#发布条件)验证固定来源、三平台附件、许可和更新行为。发布时版本、日志、下载入口与 Release 必须相互对应；仅更新源码文档时保持现有下载指向已发布版本。
